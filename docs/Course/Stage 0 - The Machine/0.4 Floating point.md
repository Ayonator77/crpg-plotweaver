# 0.4 Floating point

**Stage 0 · Module A** · 1–2 sittings · Previous: [[0.3 Bits, bytes and integers]] · Next: [[0.5 Addresses and pointers]]

## Why this matters for Plotweaver

Every position, rotation, colour, time and animation weight in the engine is a floating-point number. Their inexactness is the direct cause of a list of well-known engine problems: animation that stutters after the game has run for hours, characters that jitter far from the map's origin, surfaces that flicker where two polygons overlap, and `if a == b` checks that fail for no visible reason. Your `Frame_Time` already stores `total` as an `f64` while `dt` is an `f32`. After this lesson you'll be able to say exactly why, with numbers.

You've used `float32` and `float64` in NumPy for years. This lesson opens them up.

## The idea

### The problem floats solve

An integer type spends its bits evenly: every whole number in its range, and nothing between them. Games need 0.001 and 3,000,000 in one type. Floating point gets that range by spending bits the way **scientific notation** does.

In decimal scientific notation, 6,371,000 is written 6.371 × 10⁶. There are two parts: the **digits** (6.371) and the **exponent** (6) that says where the point goes. With a fixed number of digits, say four, you can write very large and very small numbers, but always with four digits of precision: 6.371 × 10⁶ and 6.371 × 10⁻³ are both fine, and 6,371,001 can't be told apart from 6,371,000.

A float is this, in binary.

### The layout of an `f32`

Thirty-two bits, in three fields:

```
  31 30        23 22                                0
 ┌──┬────────────┬───────────────────────────────────┐
 │S │  exponent  │             mantissa              │
 │1 │   8 bits   │              23 bits              │
 └──┴────────────┴───────────────────────────────────┘

 value  =  (-1)^S  ×  1.mantissa  ×  2^(exponent - 127)
```

- **Sign** (1 bit): 0 for positive, 1 for negative.
- **Exponent** (8 bits): which power of two to scale by. It is stored with 127 added, so that negative powers need no sign bit. A stored 127 means 2⁰. A stored 128 means 2¹.
- **Mantissa** (23 bits): the digits after the binary point. In binary scientific notation the digit before the point is always 1, so it isn't stored.

Three examples, which the worked example will print:

| Value | Sign | Exponent | Mantissa | Reading |
|---|---|---|---|---|
| 1.0 | 0 | 0111 1111 (127) | all zeros | +1.0 × 2⁰ |
| −2.0 | 1 | 1000 0000 (128) | all zeros | −1.0 × 2¹ |
| 0.1 | 0 | 0111 1011 (123) | 1001 1001 1001 1001 1001 101 | +1.6000000238… × 2⁻⁴ |

An `f64` has the same shape with more bits: 1 sign, 11 exponent, 52 mantissa.

| Type | Bytes | Mantissa bits | Reliable decimal digits |
|---|---|---|---|
| `f32` | 4 | 23 | about 7 |
| `f64` | 8 | 52 | about 15 to 16 |

### Consequence 1: most decimals can't be stored exactly

One third in decimal is 0.3333… forever. No finite number of decimal digits holds it. In binary, **one tenth** has the same problem: it is 0.000110011001100… repeating forever. A float keeps the first 23 (or 52) bits and rounds. So `0.1` in your source becomes the nearest value that *can* be stored, which is slightly off.

Each operation rounds again, and the small errors don't always cancel. In `f64`, `0.1 + 0.2` gives `0.30000000000000004`, which isn't the same stored value as `0.3`.

### Consequence 2: precision is relative, so the gaps grow

Think of the floats as marks on a ruler. Between 1 and 2 there are 2²³ marks (about 8 million), evenly spaced. Between 2 and 4 there are also 2²³ marks, spread over twice the distance. Between 4 and 8, the same number again, twice as far apart again.

```
 f32 values on the number line (not to scale):

 1        2                4                                8
 |||||||||| | | | | | | | | |   |   |   |   |   |   |   |   |
  dense       twice as sparse      twice as sparse again
```

The gap between neighbouring `f32` values near a number *v* is roughly *v* ÷ 8,000,000.

| Near | Gap between neighbouring `f32` values |
|---|---|
| 1 | 0.00000012 |
| 1,000 | 0.00006 |
| 100,000 | 0.0078 |
| 16,777,216 (2²⁴) | 2 |

That last row means an `f32` holding 16,777,216 **can't be increased by adding 1**. The answer, 16,777,217, falls between two marks and rounds back down. Likewise, adding 0.001 to 100,000 does nothing.

This is the rule to carry around: **adding a small float to a large one loses the small one's precision, or loses it entirely.**

### Consequence 3: never test floats with `==`

Two computations that should mathematically give the same result often land on neighbouring marks. So the test is whether they're close enough:

```odin
abs(a - b) <= tolerance
```

What the tolerance should be depends on the size of the numbers, since the gaps do. The lab makes you work that out.

### Special values

- **Infinity.** `1.0 / 0.0` at run time gives `+Inf`. It doesn't crash.
- **NaN,** "not a number". `0.0 / 0.0` gives NaN. Any arithmetic with a NaN gives NaN, so one bad value spreads through every calculation it touches. A character that vanishes, or a whole mesh that disappears, is very often a NaN in a matrix. And NaN is not equal to anything, **including itself**: `nan == nan` is false. That oddity is also how you detect it.

### Mixing integers and floats

Odin never converts between them for you. `f32(n) / 2` when you want a fractional result. `int(x)` to drop the fraction (it truncates toward zero).

## Worked example

Looking at the actual bits of a float. `transmute(u32)` reinterprets the same four bytes as an integer without changing them, the same operation you used on `bit_set` last lesson. Type this into `labs/a04_example/main.odin`.

```odin
package main

import "core:fmt"

main :: proc() {
	fmt.printfln("%032b", transmute(u32)f32(1.0))
	fmt.printfln("%032b", transmute(u32)f32(-2.0))
	fmt.printfln("%032b", transmute(u32)f32(0.1))

	a: f64 = 0.1
	b: f64 = 0.2
	fmt.println(a + b == 0.3)
	fmt.printfln("%.17f", a + b)

	big: f32 = 16_777_216
	fmt.println(big + 1 == big)

	zero: f32 = 0
	nan := zero / zero
	fmt.println(nan == nan, 1 / zero)
}
```

Output:

```
00111111100000000000000000000000
11000000000000000000000000000000
00111101110011001100110011001101
false
0.30000000000000004
true
false +Inf
```

Split the first three lines into 1, 8 and 23 bits by hand and match them against the table above. For 0.1, notice the repeating `1100 1100` pattern in the mantissa, cut off and rounded up at the end. That final `01` where the pattern says it should continue `00 11…` is the rounding.

`transmute` and a conversion are different things. `u32(f)` *converts*: 1.0 becomes the integer 1. `transmute(u32)f` *reinterprets*: the bits stay, the agreement changes.

And one that needs thought: a game adds `dt = 1/144` of a second to a running `f32` total, 144 times per second, for 24 hours. The true total is 86,400 seconds. Will the `f32` total be about right, a little low, or badly wrong? In which direction?

> [!success]- Output
> 1. `true`. Near 100,000 the gap between `f32` values is about 0.0078. Adding 0.001 rounds straight back.
> 2. `false`. Near 1 the gap is about 0.00000012, so 0.001 is easily visible.
> 3. `3 3.5`
> 4. `0`. The 1 was lost when it was added to 100,000,000.
> 5. `4 8`
>
> The clock: it reads about **94,900 seconds**, more than two hours fast. An addition can only land on a mark, so what really gets added is `dt` rounded to a whole number of gaps. Early on the gaps are tiny and the rounding doesn't show. A few hours in, the gap is a sizeable fraction of `dt` (0.0069), and `dt` rounds to 0.0078. From then on every frame adds 0.0078, and time runs about 12% fast. You'll measure exactly when this starts in Task 3.
