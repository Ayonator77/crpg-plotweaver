# 0.1 From notebook to executable

**Stage 0 · Module A** · 1–2 sittings · Next: [[0.2 The debugger]] · [[Curriculum Map]]

## Why this matters for Plotweaver

Everything you build from here on is a compiled program: the engine, the editor, the game, every lab. When something goes wrong at build time, the cause is in one of a few specific steps, and you fix it fastest when you know which step is complaining and what it was trying to do.

## Warm-up

This is the first lesson, so the warm-up is about what you already know. Answer in your notebook before unfolding.

1. In a Jupyter notebook you run a cell that sets `x = 5`, then delete the cell. Is `x` still there? Why?
2. When you run `python script.py`, what reads your file, and when does it find out that line 40 has a typo in a variable name?

> [!success]- Answers
> 1. Yes. The kernel is a running process that keeps all its state in memory until you restart it. The cell was only a way to send it code.
> 2. The Python interpreter reads it. It checks the grammar of the whole file up front, but it only finds a misspelled name when line 40 actually runs. If line 40 is inside an `if` that is rarely true, the typo can hide for months.

## The idea

### An interpreter and a compiler do different jobs

Python is **interpreted**. A program called the interpreter reads your code and carries it out, one step at a time, while the program is running. Your code is never turned into something the processor can run on its own. Python has to be there every time.

Odin is **compiled**. A program called the compiler reads your code once, ahead of time, and translates all of it into **machine code**: the raw numeric instructions your processor understands. The result is saved as a file, an **executable** (`.exe` on Windows). After that, the compiler is no longer needed. The executable runs by itself.

```
PYTHON                                 ODIN

 script.py                              main.odin
     │                                      │
     ▼                                      ▼  odin build     (once, ahead of time)
 ┌────────────┐                        ┌────────────┐
 │ interpreter│ reads and carries      │  compiler  │ checks everything,
 │ (running)  │ out each step,         └─────┬──────┘ translates to machine code
 └────────────┘ every time                   ▼
                                        ┌────────────┐
                                        │   linker   │ joins your code with libraries
                                        └─────┬──────┘
                                              ▼
                                         program.exe
                                              │  run it (any number of times)
                                              ▼
                                         the processor executes it directly
```

Three consequences follow, and you'll feel all of them this week.

**The compiler checks everything before anything runs.** Every name, every type, every call, in every branch. A typo on a line that would rarely run is still an error right now. This feels strict at first. It is a free test suite that runs on every build.

**Every value has a type that is fixed at compile time.** The compiler has to know how many bytes each variable needs and which processor instructions to use on it. Adding two integers and adding two decimals are different instructions. So `x` can't be an integer now and a string later.

**The program starts from nothing every run.** There's no kernel holding state. You change the code, build, run, and it begins again from the first line of `main`. The fast edit-and-poke loop you're used to is replaced by two things: a build that takes about a second, and a debugger (next lesson) for looking inside a running program.

### What the two steps do

**Compiling** turns each package of source code into machine code with some gaps in it. If your code calls `fmt.println`, the compiler emits "call the procedure named `fmt.println`" without yet knowing where that procedure will end up.

**Linking** fills the gaps. The linker takes your compiled code, the compiled code of every library you use, and joins them into one file, replacing each "call the thing named X" with the actual location of X.

This is why there are two families of build errors. A **compile error** means your source is wrong: a type doesn't match, a name doesn't exist. A **link error** means every file was fine on its own, but something they refer to couldn't be found when joining them, usually a missing library. Compile errors point at a line of your code. Link errors mention "unresolved external symbol" and point at no line at all.

### Just enough Odin to start

You've typed some Odin already. Treat this as the reference card for the lab.

```odin
package main                  // every file belongs to a package; a folder is one package

import "core:fmt"             // use the fmt package from Odin's core library

MAX_ROLL :: 20                // ::  declares a constant (fixed at compile time)

roll_total :: proc(roll: int, modifier: int) -> int {   // a procedure is also a constant
	return roll + modifier
}

main :: proc() {              // the program starts here
	dc := 14                  // :=  declares a variable; its type comes from the value (int)
	bonus: f32 = 2.5          // name: type = value   when you want to state the type
	dc = 15                   // =   assigns to a variable that already exists

	for roll in 1..=MAX_ROLL {        // 1..=20 includes 20;  0..<20 stops at 19
		if roll_total(roll, 4) >= dc {
			fmt.println(roll, "succeeds")
		}
	}
}
```

Three things here differ from Python and will trip you up for a few days:

- **Declaring and assigning are different operations.** `x := 5` creates `x`. `x = 6` changes it. Writing `x = 6` for a name that doesn't exist is an error, which catches typos that Python would silently turn into a new variable.
- **Blocks are marked with braces,** not indentation. Indentation is for you.
- **Types don't mix on their own.** `dc + bonus` is an error, because one is an `int` and one is an `f32`. You convert explicitly: `f32(dc) + bonus`.

Read these sections of the [Odin overview](https://odin-lang.org/docs/overview/) before the lab, with the lesson closed: *Hello World*, *Variable declarations*, *Constant declarations*, *Control flow statements* (`for`, `if`, `switch`), *Procedures*. Skip anything about memory or pointers for now.

## Worked example

A table of every d20 result against DC 14 with a +4 modifier. Type it into `labs/a01_example/main.odin`. Don't paste it.

```odin
package main

import "core:fmt"

MAX_ROLL :: 20

roll_total :: proc(roll: int, modifier: int) -> int {
	return roll + modifier
}

main :: proc() {
	dc := 14
	modifier := 4
	for roll in 1..=MAX_ROLL {
		total := roll_total(roll, modifier)
		if total >= dc {
			fmt.println("roll", roll, "total", total, "success")
		} else {
			fmt.println("roll", roll, "total", total, "fail")
		}
	}
}
```

From the repo root:

```
odin run labs/a01_example
```

It prints twenty lines. The first success is `roll 10 total 14 success`.

`odin run` builds the program, runs it, and deletes the executable afterwards. To keep the executable, build it:

```
odin build labs/a01_example -out:bin/a01_example.exe
bin\a01_example.exe
```

```odin
package main

import "core:fmt"

main :: proc() {
	dc: int = 14
	bonus := 2.5
	total := dc + bonus
	unused := 3
	fmt.println(totl)
}
```

Build this one with `odin build <folder> -vet`. The `-vet` flag turns on extra checks. You'll use it from now on.

> [!success]- What happens
> 1. Yes. The executable is a complete, separate file. It has no link back to the source.
> 2. Still 10. The executable was made from the old source. Nothing changes until you build again. Forgetting to rebuild, or running a stale executable, is a real and common way to lose an hour.
> 3. All four, in one build: line 8 `'total' declared but not used`, line 8 `Mismatched types in binary expression 'dc + bonus' : 'int' vs 'f64'`, line 9 `'unused' declared but not used`, line 10 `Undeclared name: totl`. Each message starts with `file(line:column)`. Notice that `bonus := 2.5` became an `f64`, the default type for a decimal constant.

## Check yourself

Close the lesson. Answer in your notebook.

1. What does the compiler produce, and what does the linker add?
2. Give two reasons the compiler must know every variable's type before the program runs.
3. You get an error that mentions an "unresolved external symbol" and no line number. Which step failed, and what kind of cause do you look for?
4. What is the difference between `:=`, `=` and `::`?
5. Your program prints the old output after you changed the source. Name two possible causes.
6. Why does a compiled language find a typo on a rarely-run line, when Python doesn't?

> [!success]- Answers
> 1. The compiler produces machine code for your source, with references to things defined elsewhere left open. The linker joins that with library code and resolves the references, giving one executable.
> 2. It has to reserve the right number of bytes for it, and it has to choose the right processor instructions for operations on it.
> 3. Linking. The source was fine. Something it refers to wasn't found when joining: usually a library that wasn't given to the linker, or a foreign procedure whose name doesn't match.
> 4. `:=` declares a new variable and gives it a value. `=` assigns to an existing variable. `::` declares a constant.
> 5. You didn't rebuild. Or you rebuilt, the build failed, and you ran the old executable that was still there. (A third: you're running a different executable from the one you built.)
> 6. The compiler translates and checks every line of the program ahead of time. Python only resolves a name at the moment the line runs.
