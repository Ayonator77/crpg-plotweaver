# 0.2 The debugger

**Stage 0 · Module A** · 1–2 sittings · Previous: [[0.1 From notebook to executable]] · Next: [[0.3 Bits, bytes and integers]]

## Why this matters for Plotweaver

In a notebook you inspect things by running another cell. A compiled program has no cells. The debugger is how you look inside one while it runs: stop it on any line, read every variable, walk forward one line at a time. An engine has too much going on per frame to understand from printed text, and from Lesson 0.5 onward the bugs you meet (bad pointers, memory overwritten by something else) can't be found any other way. You have the RAD Debugger installed at `F:\raddbg`. This lesson makes it a habit.

## The idea

### What a debugger is

A debugger is a program that runs *your* program under its control. It can pause it, show you its memory, and let it continue. It needs two things: the executable, and the debug information (`.pdb`) that says "this machine instruction came from line 12 of `main.odin`" and "the variable `sum` lives at this location".

So you always build with `-debug` when you intend to debug. Without it the debugger can still run the program, but it can only show you raw machine instructions.

### The five things you do with it

| You want to | It's called | RAD Debugger key |
|---|---|---|
| Stop when execution reaches a certain line | **Breakpoint** | **F9** on the line toggles one |
| Start, or continue to the next breakpoint | **Run** | **F5** |
| Execute the current line and stop on the next one | **Step over** | **F10** |
| Go *inside* the procedure called on this line | **Step into** | **F11** |
| Finish the current procedure and stop back in its caller | **Step out** | **Shift + F11** |

Stop everything with **Shift + F5**. **F1** opens the palette, which lists every command and its key, so you never need to memorise more than this table.

While the program is paused, three panels matter:

- **Locals** shows every variable in the current procedure and its value right now.
- **Watch** is a table where you type your own expressions (`values[i]`, `sum / 6`) and see them evaluated at every stop.
- **Call Stack** shows how you got here: the current procedure, the one that called it, the one that called that, down to `main`. Click a row to see that caller's variables.

```
Call Stack while paused inside average():

   average        ← you are here            (its locals: values, sum, i)
   main           ← called average          (its locals: rolls, damage)
```

### Step over or step into?

The line about to run is highlighted. If it contains a call:

- **Step over** runs the whole call and stops on the next line. Use it when you trust the procedure.
- **Step into** stops on the first line inside it. Use it when the procedure is the suspect.

If you step into something you didn't mean to (a library routine), **step out** brings you back.

### Debugging is a method, and the debugger is the instrument

Poking around at random with a debugger is only slightly better than poking at random with print statements. The method is the scientific one, and you already use it when a model won't train:

1. **State the symptom precisely.** "The average prints 9, and it should be 12."
2. **Form a hypothesis** about where the program's actual state first departs from what you expect.
3. **Pick a place to look** that would confirm or kill the hypothesis, and put a breakpoint there.
4. **Predict the values** you should see there, before you look.
5. **Look.** If they match, the problem is later: move the breakpoint forward. If they don't, it's earlier or right here.
6. Repeat until you're standing on the first wrong value. The bug is on the line that produced it.

Step 4 matters most. If you look without first predicting, everything on screen seems plausible and you learn nothing from it.

### Why not just print?

Printing works, and experienced programmers do it sometimes. But each print costs an edit and a rebuild, shows only what you thought to ask for, and has to be removed afterwards. Paused in a debugger, every variable is already visible, including the ones you didn't suspect. For this module the rule is strict: **no print statements for debugging.** It's a training constraint to make the debugger your reflex.

## Worked example

Type this into `labs/a02_example/main.odin`. It is correct. You're going to watch it run.

```odin
package main

import "core:fmt"

count_successes :: proc(modifier: int, dc: int) -> int {
	count := 0
	for roll in 1..=20 {
		if roll + modifier >= dc {
			count += 1
		}
	}
	return count
}

main :: proc() {
	easy := count_successes(4, 10)
	hard := count_successes(4, 20)
	fmt.println(easy, hard)
}
```

Build with debug information and open it in the debugger:

```
odin build labs/a02_example -debug -out:bin/a02_example.exe
raddbg bin\a02_example.exe
```

If `raddbg` isn't found, use the full path `F:\raddbg\raddbg.exe`.

Then do exactly this, and check each observation:

1. **Ctrl + O**, open `labs/a02_example/main.odin`. Click on the line `easy := count_successes(4, 10)` and press **F9**. A breakpoint marker appears.
2. **F5**. The program starts and pauses on that line. The line has *not* run yet.
3. Look at **Locals**. `easy` and `hard` are there already, holding whatever was in that memory. They have locations before they have meaningful values.
4. **F11** to step into `count_successes`. Locals now shows `modifier = 4`, `dc = 10`, and the Call Stack has two rows.
5. **F10** repeatedly. Watch `roll` climb and `count` stay at 0. Predict: at which value of `roll` does `count` first become 1? (4 + roll ≥ 10.) Keep stepping and see whether you were right.
6. Stepping twenty times is tedious. Click the `return count` line, press **F9**, then **F5**. You run straight to it. `count` should be 15.
7. **Shift + F11** to step out. You're back in `main`.
8. In the **Watch** panel, type `easy + hard` as a new expression. **F10** twice and watch it settle to 20.
9. **F5** to let the program finish.

You have now used every control in the table.

> 1. Fifteen times, once per successful roll (rolls 6 to 20).
> 2. `easy` is 15, because the first call has finished and its result was stored. `hard` holds leftover or zero memory, because the second call hasn't returned yet, so nothing has been assigned to it.

## Lab

### Task 1 — Find three bugs without printing

Type this into `labs/a02_bugs/main.odin` exactly as written. It has three bugs. Don't hunt for them by reading. That's the point of the exercise.

```odin
package main

import "core:fmt"

average :: proc(values: []int) -> int {
	sum := 0
	for i in 0..<len(values) - 1 {
		sum += values[i]
	}
	return sum / len(values)
}

highest :: proc(values: []int) -> int {
	best := 0
	for v in values {
		if v > best {
			best = v
		}
	}
	return best
}

main :: proc() {
	rolls := []int{12, 7, 19, 3, 15, 20}
	damage := []int{-4, -9, -2}
	fmt.println("average roll:", average(rolls))
	fmt.println("highest roll:", highest(rolls))
	fmt.println("smallest penalty:", highest(damage))
}
```

It prints:

```
average roll: 9
highest roll: 20
smallest penalty: 0
```

By hand, the average of the rolls is 76 ÷ 6 ≈ 12.67, and the smallest penalty (the value closest to zero) is −2.

Rules:

- The only `fmt.println` calls allowed are the three already there.
- For **each** wrong output, write the six steps of the method in your notebook as you do them: symptom, hypothesis, where you'll look, the values you predict there, what you saw, conclusion.
- Fix each bug with the smallest change that is actually correct, then rebuild and confirm.

One of the three outputs can't be made exactly right while the procedure returns an `int`. Decide what the procedure *should* return, and change it.

**It works when** the output is a correct average with its fractional part, 20, and −2, and your notebook has three filled-in method records.

> [!hint]- Hint 1 (average)
> Break on `return`. Before looking, work out by hand what `sum` should be at that point. Then look.

> [!hint]- Hint 2 (average)
> If `sum` is wrong, the loop is the suspect. Put a watch on `i` and on `values[i]`, and count how many times the loop body runs.

> [!hint]- Hint 3 (average)
> Once `sum` is right, watch the expression `sum / len(values)` and compare it with your calculator. What does `/` do when both sides are integers? Lesson 0.3 covers this properly. For now, the worked example of Lesson 0.1 showed how to convert a value to another type.

> [!hint]- Hint 1 (highest)
> Step through the call with `damage`. Watch `best`. Does the `if` body ever run? Why not?

> [!hint]- Hint 2 (highest)
> The bug is in what `best` starts as. What starting value would be right for *any* list, including one that is all negative? There's more than one good answer.

## Check yourself

1. What two files does the debugger need, and what does each give it?
2. You're paused on a line. Has that line executed?
3. When do you step over, and when do you step into?
4. What does the Call Stack show, and what happens when you click a row that isn't the top one?
5. List the six steps of the debugging method. Which one do people skip, and what does skipping it cost?
6. A variable shows a strange large number before its declaration line has run. Is that a bug?

> [!success]- Answers
> 1. The executable (the machine code to run) and the `.pdb` debug information (the mapping from machine code back to source lines, variable names and types).
> 2. No. The highlighted line is the next one to run.
> 3. Over when the called procedure isn't under suspicion and you only want its result. Into when the problem might be inside it.
> 4. The chain of calls that are currently in progress, newest on top. Clicking a lower row shows that caller's source position and local variables as they are right now.
> 5. State the symptom, form a hypothesis, choose where to look, predict the values, look, conclude and repeat. People skip the prediction. Without it, whatever you see looks reasonable and you can't tell right from wrong.
> 6. No. The variable's storage exists for the whole procedure, and before the declaration runs it holds whatever was there before. (Odin sets a variable to zero *at its declaration*, so after that line it's well-defined.)
