# 0.5 Addresses and pointers

**Stage 0 · Module A** · 2 sittings · Previous: [[0.4 Floating point]] · Next: [[0.6 Arrays, slices and strings]]

## Why this matters for Plotweaver

Your engine code is already full of pointers: `platform.init(&host, ...)`, `proc(state: ^State)`, `&mvp[0, 0]` handed to OpenGL. Every system gets its state through one. Later, the big architectural questions (how entities refer to each other, why handles beat pointers, why growing an array can corrupt the game) are all questions about addresses. This is the most important lesson in the module, and nothing after it makes sense without it.

## The idea

### Memory is one long row of numbered bytes

Forget variables for a moment. Your program's memory is a single enormous row of bytes. Each byte has a number, counting up from zero. That number is the byte's **address**.

```
 address:   ...  1000  1001  1002  1003  1004  1005  1006  1007  ...
              ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
 contents:    │  07 │  00 │  00 │  00 │  2A │  00 │  00 │  00 │
              └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
```

That is all there is. Everything else is a way of naming parts of this row.

### A variable is a name for some of those bytes

When you write `a: i32 = 7`, the compiler picks four bytes in the row (an `i32` is four bytes), and from then on `a` *means* those four bytes. Writing `a = 9` puts new bits into those four bytes. Reading `a` reads them.

```
            a (i32, 4 bytes at address 1000)     b (i32, 4 bytes at address 1004)
              ┌─────┬─────┬─────┬─────┐            ┌─────┬─────┬─────┬─────┐
              │  07 │  00 │  00 │  00 │            │  2A │  00 │  00 │  00 │
              └─────┴─────┴─────┴─────┘            └─────┴─────┴─────┴─────┘
               1000  1001  1002  1003               1004  1005  1006  1007
```

Here is the first big difference from Python.

```python
a = [1, 2, 3]
b = a          # b is a second name for the SAME list
b[0] = 99      # a[0] is now 99 too
```

In Python a variable is a label tied to an object that lives somewhere else, and assignment ties a second label to the same object.

```odin
a := [3]int{1, 2, 3}
b := a         // b is its own 24 bytes; the contents of a are COPIED into them
b[0] = 99      // a[0] is still 1
```

In Odin a variable **is** its bytes, and assignment **copies bytes** from one place to another. The two are independent afterwards. This holds for every type: integers, arrays, structs, all of them.

### A pointer is a variable that holds an address

Since addresses are numbers, you can store one in a variable. A variable that holds the address of something is a **pointer**.

```odin
a: i32 = 7
p: ^i32 = &a      // p holds the address of a
```

- `&a` means "the address of `a`". Here that's 1000.
- `^i32` is the type "pointer to an `i32`". Read the `^` as "points to".
- `p` is an ordinary variable with its own bytes (eight of them, because addresses on your machine are 64 bits). Their content is the number 1000.

```
            a  (i32)                             p  (^i32, 8 bytes)
              ┌──────────┐                         ┌──────────┐
   1000 →     │    7     │   ◄─────────────────────│   1000   │    ← at address 2000
              └──────────┘                         └──────────┘
```

The arrow in the picture isn't anything special in memory. It's the fact that the number stored in `p` happens to be the address where `a` lives.

### Following a pointer

`p^` means "the thing `p` points to": go to the address stored in `p` and treat what's there as an `i32`. This is called **dereferencing**.

```odin
fmt.println(p^)   // 7     read through the pointer
p^ = 9            //       write through the pointer
fmt.println(a)    // 9     a changed, because p^ and a are the same four bytes
```

Notice where the `^` goes. In a type it comes before, `^i32`, a pointer *to* an i32. On a value it comes after, `p^`, *follow* p.

The pointer's type tells the compiler how to read what's at the address: how many bytes, and with which agreement. An address alone doesn't say. That is "a type is an agreement" again.

### Why pointers exist: sharing without copying

**Procedure arguments are copies.** When you call a procedure, each argument's bytes are copied into fresh variables that belong to the procedure. Changing them inside changes the copies.

```odin
Hero :: struct {
	health: i32,
	focus:  i32,
}

heal_copy :: proc(h: Hero) {     // h is a private copy of the caller's Hero
	h := h                       // (Odin parameters can't be modified; this makes a local you can)
	h.health += 5                // changes the copy, which then vanishes
}

heal :: proc(h: ^Hero) {         // h is a copy of an ADDRESS
	h.health += 5                // follows the address and changes the caller's Hero
}
```

`heal(&hero)` copies eight bytes, the address, and through it the procedure reaches the original. This is the reason nearly every procedure in your engine takes `state: ^State`. There are two motives, and you should always know which one applies:

1. **To modify the caller's data.** `heal` needs to.
2. **To avoid copying something large.** Copying an 8-byte address is cheaper than copying a 2,000-byte struct.

Two conveniences in the snippet above:

- `h.health` on a pointer works directly. Odin follows the pointer for you when you use `.` on it, so you don't write `h^.health`.
- Odin's parameters are immutable. You can't assign to `h` itself. This is why you'll see `mvp := mvp` in your `renderer.odin`: it makes a modifiable local copy so its address can be taken.

### `nil`: a pointer to nothing

A pointer that hasn't been given an address holds 0, written `nil`. It points at nothing valid. Following a `nil` pointer crashes the program immediately, because the operating system keeps the lowest addresses off-limits precisely to catch this.

A crash on `nil` is the *good* outcome. The bad kind of pointer bug is one that points at memory that used to be something else. It doesn't crash. It quietly reads or damages unrelated data. You'll meet those in Module B.

A procedure that returns a pointer and might have nothing to return gives back `nil`, and the caller has to check:

```odin
target := find_target(...)
if target != nil {
	target.health -= 3
}
```

### Aliasing

Two pointers holding the same address are called **aliases**. A write through one is visible through the other, since there's only one set of bytes.

```odin
p := &hero
q := p            // copies the address, not the Hero
q.health = 1      // p.health is now 1 as well
```

Assignment still copied bytes here. It copied the eight bytes of the address. Aliasing is how Python's lists behaved in the example above: Python variables are pointers under the hood, and you never see the `^`.

### Looking at raw bytes

A pointer can be reinterpreted to view the same memory under a different agreement. This views the four bytes of a `u32` as four separate `u8`s:

```odin
value: u32 = 0x11223344
bytes := cast(^[4]u8)&value
fmt.printfln("%x", bytes^)      // [44, 33, 22, 11]
```

The bytes come out **backwards**. Your processor stores the *least* significant byte at the *lowest* address. This is called **little-endian**, and every PC and phone today does it. It matters whenever you read a file format byte by byte, which you'll do at the gate.

```
 value = 0x11223344          address:  1000  1001  1002  1003
                                       ┌────┬────┬────┬────┐
                                       │ 44 │ 33 │ 22 │ 11 │
                                       └────┴────┴────┴────┘
                                        low byte first
```

## Worked example

Type into `labs/a05_example/main.odin`. Before you run it, cover the output below and predict each printed line.

```odin
package main

import "core:fmt"

Hero :: struct {
	health: i32,
	focus:  i32,
}

heal_copy :: proc(h: Hero) {
	h := h
	h.health += 5
}

heal :: proc(h: ^Hero) {
	h.health += 5
}

main :: proc() {
	a: i32 = 7
	p: ^i32 = &a
	fmt.println(p^)
	p^ = 9
	fmt.println(a)
	fmt.printfln("%p %p", &a, p)

	b := a
	b = 100
	fmt.println(a, b)

	hero := Hero{health = 10, focus = 3}
	heal_copy(hero)
	fmt.println(hero.health)
	heal(&hero)
	fmt.println(hero.health)

	fmt.println(size_of(p), size_of(^Hero))
}
```

Output (your addresses will differ, and will differ between runs):

```
7
9
0xCB6FDFFD74 0xCB6FDFFD74
9 100
10
15
8 8
```

- Lines 1–2: reading and writing through `p` reads and writes `a`.
- Line 3: `&a` and `p` print the same address. `%p` formats a pointer.
- Line 4: `b := a` copied the value. Changing `b` left `a` alone.
- Line 5: `heal_copy` changed its own copy. `hero.health` is still 10.
- Line 6: `heal` followed the address. Now it's 15.
- Line 7: a pointer is 8 bytes whatever it points to. A pointer to a 4-byte `i32` and a pointer to a 2,000-byte struct are the same size.

Now run it in the debugger. Break on `p^ = 9`. Add `p` and `&a` to the Watch panel and confirm they match. Use the palette's **Go To Memory** on `&a`, find the four bytes `07 00 00 00`, then step once and watch them change.
