# 0.3 Bits, bytes and integers

**Stage 0 · Module A** · 2 sittings · Previous: [[0.2 The debugger]] · Next: [[0.4 Floating point]]

## Why this matters for Plotweaver

Your input code already stores the whole keyboard as `bit_set[Key; u128]`: one bit per key. A surface cell on the ground will be a few bits of type, a few bits of flags and a small timer, because the map has hundreds of thousands of them. Colours are four bytes. Every file format you'll parse (glTF, textures) is defined byte by byte. A character's health going below zero in an unsigned integer becomes four billion. You can't design or debug any of that without being fluent in what an integer physically is.

## The idea

### A bit, a byte

Memory is made of switches that are off or on. One switch is a **bit**: 0 or 1. Eight bits in a row are a **byte**. A byte is the unit memory is measured and addressed in.

With 8 bits there are 2 × 2 × 2 × 2 × 2 × 2 × 2 × 2 = 256 possible patterns. What a pattern *means* is not stored anywhere. The bits `01000001` are the number 65, or the letter `A`, or a shade of grey, depending on what the code reading them decides. **A type is an agreement about how to interpret some bytes.** Keep that sentence. It explains half of this module.

### Counting in binary

Decimal has ten digits, and each position is worth ten times the one to its right: 1s, 10s, 100s. Binary has two digits, and each position is worth twice the one to its right: 1s, 2s, 4s, 8s.

```
 position value:   128  64  32  16   8   4   2   1
 bits:               0   1   0   0   0   0   0   1
                         64                    + 1   = 65
```

The rightmost bit is called **bit 0** or the least significant bit. The leftmost of a byte is **bit 7**, the most significant.

Largest value in a byte: all eight bits on, 128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = 255. So a byte holds 0 to 255. With n bits you get 2ⁿ patterns, holding 0 to 2ⁿ − 1.

### Hexadecimal: binary for humans

Long binary numbers are unreadable. **Hexadecimal** (base 16) fixes that, because one hex digit is exactly four bits.

| Hex | Bits | | Hex | Bits |
|---|---|---|---|---|
| 0 | 0000 | | 8 | 1000 |
| 1 | 0001 | | 9 | 1001 |
| 2 | 0010 | | A | 1010 |
| 3 | 0011 | | B | 1011 |
| 4 | 0100 | | C | 1100 |
| 5 | 0101 | | D | 1101 |
| 6 | 0110 | | E | 1110 |
| 7 | 0111 | | F | 1111 |

A byte is always two hex digits. `0xFF` is `1111 1111`, which is 255. `0x41` is `0100 0001`, which is 65. You translate one digit at a time, with no arithmetic. Debuggers, memory views and file formats all speak hex, so learn the table.

In Odin source: `0b0100_0001` is binary, `0x41` is hex, and underscores are allowed anywhere in a number for readability (`1_000_000`).

### Odin's integer types

| Type | Bytes | Range |
|---|---|---|
| `u8` | 1 | 0 to 255 |
| `u16` | 2 | 0 to 65,535 |
| `u32` | 4 | 0 to 4,294,967,295 |
| `u64` | 8 | 0 to about 1.8 × 10¹⁹ |
| `i8` | 1 | −128 to 127 |
| `i16` | 2 | −32,768 to 32,767 |
| `i32` | 4 | about ±2.1 billion |
| `i64` | 8 | about ±9.2 × 10¹⁸ |
| `int` | 8 on your machine | same as `i64` |

`u` means unsigned (no negatives). `i` means signed. `int` is the default and is as wide as the machine's addresses, 8 bytes on a 64-bit system. `size_of(T)` gives a type's size in bytes, and `min(T)` and `max(T)` give its limits.

Python integers grow without limit. These don't. That is the trade: a fixed size means the processor handles them in a single instruction, and it means they can overflow.

### Overflow

A `u8` holding 250 has 10 added to it. The true answer, 260, needs nine bits. There are only eight. The ninth is dropped, and what's left is 4.

```
   250   =    1111 1010
 +  10   =    0000 1010
 ───────────────────────
   260   =  1 0000 0100     ← nine bits
              0000 0100     ← the eight that fit  =  4
```

It behaves like a car's odometer rolling over. The same happens going down: a `u32` at 0 minus 1 becomes 4,294,967,295. In Odin this wrap-around is the defined behaviour for all integer types. It isn't an error and nothing warns you at run time. When a value is known at compile time, the compiler does refuse: `x: u8 = 256` won't build.

Wrap-around in an unsigned health value is a classic game bug: the hero takes 12 damage at 10 health and now has 4 billion.

### Negative numbers: two's complement

Signed types use the top bit differently. In an `i8`, bit 7 is worth **−128** in place of +128. Everything else is the same.

```
 position value:  -128  64  32  16   8   4   2   1
     1111 1111  =  -128 + 127                        = -1
     1000 0000  =  -128                              = -128
     0111 1111  =         127                        = 127
```

This scheme is called **two's complement**. Its advantage is that the processor's ordinary addition circuit gives correct answers for negatives with no special cases: `1111 1111` (−1) plus `0000 0001` (1) is `1 0000 0000`, the ninth bit drops, leaving 0.

Two things follow. An `i8` at 127 plus 1 becomes −128. And the same eight bits `1111 1111` are 255 as a `u8` and −1 as an `i8`. The bits didn't change. The agreement did.

### Converting between sizes

Conversions are always written out: `u8(x)`, `i32(x)`, `f32(x)`.

- **Widening** (`u8` → `u32`) always keeps the value.
- **Narrowing** (`int` → `u8`) keeps only the low bits. 300 is `1 0010 1100`. Its low eight bits are `0010 1100`, which is 44. So `u8(300)` computed at run time gives 44.

### Integer division

`/` between two integers drops the fraction: `7 / 2` is 3, and `-7 / 2` is −3 (it rounds toward zero). `%` gives the remainder: `7 % 2` is 1. If you want 3.5, at least one side must be a floating-point value: `f32(7) / 2`.

### Operating on bits

These work on each bit position independently.

| Operator | Name | Result bit is 1 when | Example on `1010` and `0110` |
|---|---|---|---|
| `&` | AND | both are 1 | `0010` |
| `\|` | OR | either is 1 | `1110` |
| `~` (between two values) | XOR | they differ | `1100` |
| `~` (in front of one value) | NOT | the bit was 0 | `~1010` is `0101` |
| `&~` | AND NOT | left is 1 and right is 0 | `1000` |
| `<<` | shift left | moves bits toward the top, zeros come in | `0011 << 2` is `1100` |
| `>>` | shift right | moves bits toward the bottom | `1100 >> 2` is `0011` |

Shifting left by n multiplies by 2ⁿ. `1 << n` is the number with only bit n set, and that is the building block for everything else.

**A mask** is a value whose 1 bits select the bits you care about. The four standard moves on a set of flags:

```odin
flags: u8 = 0b0000_0101

flags | (1 << 3)        // set bit 3        → 0000_1101
flags &~ (1 << 0)       // clear bit 0      → 0000_0100
flags ~ (1 << 2)        // toggle bit 2     → 0000_0001
flags & (1 << 2) != 0   // test bit 2       → true
```

### `bit_set`: flags with names

Doing that by hand is error-prone, so Odin has a built-in type for it. A `bit_set` over an enum uses one bit per enum value.

```odin
Condition :: enum u8 { Prone, Slowed, Stunned, Restrained }

conditions: bit_set[Condition; u8]      // one byte, four of its bits used
conditions += {.Prone, .Stunned}        // set
conditions -= {.Prone}                  // clear
if .Stunned in conditions { }           // test
```

`Prone` is enum value 0, so it's bit 0. `Stunned` is value 2, so it's bit 2. This is exactly what `keys_down: bit_set[Key; u128]` in your `input.odin` is: 128 bits, one per key, tested with `in`.

## Worked example

Packing a colour's four channels into one `u32`, and getting one back out. Type it into `labs/a03_example/main.odin`.

```odin
package main

import "core:fmt"

// Layout, from the top byte down:  RRRRRRRR GGGGGGGG BBBBBBBB AAAAAAAA
pack_rgba :: proc(r, g, b, a: u8) -> u32 {
	return u32(r) << 24 | u32(g) << 16 | u32(b) << 8 | u32(a)
}

green_of :: proc(color: u32) -> u8 {
	return u8((color >> 16) & 0xFF)
}

main :: proc() {
	orange := pack_rgba(255, 115, 26, 255)
	fmt.printfln("%08x", orange)
	fmt.printfln("%032b", orange)
	fmt.println(green_of(orange))
}
```

Output:

```
ff731aff
11111111011100110001101011111111
115
```

Read it slowly.

- `u32(r)` widens the byte to 32 bits **before** shifting. A `u8` shifted left by 24 would push every bit off the end.
- `<< 24` moves red into the top byte. Green goes to the next byte, and so on. `|` merges them, which works because no two occupy the same bits.
- To read green back: `>> 16` slides the green byte down to the bottom, and `& 0xFF` keeps only the low eight bits, throwing away the red that slid down with it.
- In the hex output you can read the four channels straight off, two digits each: `ff` `73` `1a` `ff`. That is why hex is used.

The format verbs: `%x` prints hex, `%b` binary, `%d` decimal. `%08x` pads with zeros to 8 digits.
