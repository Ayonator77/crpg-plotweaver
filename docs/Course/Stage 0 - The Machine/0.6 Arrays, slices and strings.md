# 0.6 Arrays, slices and strings

**Stage 0 · Module A** · 2 sittings · Previous: [[0.5 Addresses and pointers]] · Next: [[Gate A - Hex dump]]

## Why this matters for Plotweaver

A mesh is an array of vertices. An animation is an array of keyframes. The party is an array of characters. A loaded file is an array of bytes. A shader's source is a string, which is an array of bytes too. The engine's hot loops will all be "walk an array". How arrays are laid out, and how a procedure can look at part of one without copying it, underlies both the performance work in Module C and every data structure you'll build in Module B.

You have a head start. A slice is nearly the same thing as a NumPy array view.

## The idea

### A fixed array: values in a row

`[5]int` is five `int`s placed one directly after another in memory. Nothing else is stored: no length, no header. The length is part of the *type*, known at compile time.

```odin
a := [5]int{10, 20, 30, 40, 50}
```

```
 address:   1000      1008      1016      1024      1032
          ┌─────────┬─────────┬─────────┬─────────┬─────────┐
     a    │   10    │   20    │   30    │   40    │   50    │      size_of(a) = 40 bytes
          └─────────┴─────────┴─────────┴─────────┴─────────┘
            a[0]      a[1]      a[2]      a[3]      a[4]
```

Indexing is arithmetic on addresses: `a[i]` lives at *(address of a) + i × (size of one element)*. `a[3]` is at 1000 + 3 × 8 = 1024. That is why indexing takes the same time whatever the index, and why indices start at 0: the index is the distance from the start.

Two properties follow from "a variable is its bytes":

- **An array is a value.** `b := a` copies all 40 bytes. Passing `a` to a procedure copies all 40 bytes.
- **`[5]int` and `[6]int` are different types.** A procedure taking `[5]int` can't take an array of six.

That second property makes fixed arrays useless as general procedure parameters. You'd need a different `sum` for every length. The fix is the slice.

Fixed arrays of numbers support arithmetic directly, element by element, which you're already using for colours and positions: `[3]f32{1, 2, 3} * 2 + {1, 1, 1}` is `{3, 5, 7}`.

### A slice: a pointer and a length

A **slice**, written `[]int`, is a small struct with two fields:

```
 a slice ([]int) is 16 bytes:
          ┌──────────────────┬──────────────────┐
          │  data: address   │   len: count     │
          └──────────────────┴──────────────────┘
```

It doesn't contain any elements. It **refers to** a run of elements that live somewhere else. You make one by slicing an array:

```odin
a := [5]int{10, 20, 30, 40, 50}
s := a[1:4]       // elements 1, 2 and 3.  Start is included, end is not.
```

```
                  1000      1008      1016      1024      1032
                ┌─────────┬─────────┬─────────┬─────────┬─────────┐
          a     │   10    │   20    │   30    │   40    │   50    │
                └─────────┴─────────┴─────────┴─────────┴─────────┘
                            ▲
                            │         s[0]      s[1]      s[2]
          s    ┌────────────┴───┬───────┐
               │  data = 1008   │ len=3 │
               └────────────────┴───────┘
```

`s[0]` is `a[1]`. They aren't equal copies, they're the same eight bytes. Writing `s[0] = 21` changes `a[1]`. This is aliasing from last lesson, in its most common form.

The slicing forms: `a[1:4]`, `a[:3]` (from the start), `a[2:]` (to the end), `a[:]` (all of it).

This is the model behind NumPy. `arr[1:4]` in NumPy gives a *view* that shares memory with `arr`: a pointer to the data, a shape, and a data type. An Odin slice is the one-dimensional version of that.

### Why slices are how procedures take arrays

```odin
sum :: proc(values: []int) -> int {
	total := 0
	for v in values {
		total += v
	}
	return total
}

sum(a[:])        // the whole array
sum(a[1:4])      // part of it
```

Passing a slice copies 16 bytes, the pointer and the length, whatever the array's size. One procedure works for every length. And since the slice refers to the caller's elements, the procedure can modify them through it. A slice parameter is a pointer parameter that also knows how many elements there are.

### Bounds checking

A slice knows its length, so Odin checks every index. `s[7]` on a three-element slice stops the program with a message naming the file, line, index and length. Without the check, `s[7]` would compute an address past the end and read or damage whatever is there, which is the classic memory bug in C. The check costs a comparison per access. It can be turned off for release builds once code is trusted (`-no-bounds-check`). Leave it on.

### A slice doesn't own anything

A slice is only a view. It has no say over how long the elements it points to stay alive. If the array goes away while a slice still refers to it, the slice points at dead memory, and nothing warns you. Module B is about exactly this question of who owns memory and for how long. For now, every slice in this lesson views an array that lives in `main`, which outlasts everything.

There's a third array type, `[dynamic]int`, which can grow. It's a slice plus ownership plus a capacity. You'll build your own in Lesson 0.10 before using the built-in one.

### Strings are slices of bytes

A `string` in Odin has exactly the same shape as a slice: a pointer to bytes and a length. It's 16 bytes, and the text lives elsewhere.

```odin
name := "Zoë"
len(name)       // 4, not 3
```

Four, because `len` counts **bytes** and the text is stored as **UTF-8**. In UTF-8, the characters of basic English take one byte each, and every other character takes two, three or four. `ë` takes two.

```
 "Zoë"  →   5A    6F    C3  AB
            Z     o     ë (two bytes)
```

So there are two ways to walk a string, and they give different things:

```odin
for i in 0..<len(name) {
	fmt.printf("%02x ", name[i])    // by index: BYTES →  5a 6f c3 ab
}

for r in name {
	fmt.print(r, "")                // for-in:   CHARACTERS (runes) →  Z o ë
}
```

`name[i]` is a `u8`. The `for r in name` loop decodes UTF-8 for you and gives each character as a `rune`, a 32-bit value that can hold any character.

Three more facts:

- **Strings are immutable.** You can't write `name[0] = 'A'`. A string literal's bytes are stored inside the executable itself.
- **Slicing a string gives a string** that views part of the same bytes: `name[0:2]` is `"Zo"`. Slice at a byte position inside a multi-byte character and you get broken text.
- **`cstring` is a different type.** C libraries (SDL, OpenGL) expect text as a bare pointer with a zero byte marking the end, and no length. That's why your platform code converts. You'll look at this properly when you bind C libraries in Stage 2.

## Worked example

Type into `labs/a06_example/main.odin`. Predict each line of output before running.

```odin
package main

import "core:fmt"

main :: proc() {
	a := [5]int{10, 20, 30, 40, 50}
	b := a
	b[0] = 99
	fmt.println(a[0], b[0], size_of(a))

	s := a[1:4]
	fmt.println(s, len(s), size_of(s))

	s[0] = 21
	fmt.println(a)

	t := a[2:]
	t[0] = 31
	fmt.println(s, t)

	name := "Zoë"
	fmt.println(len(name), size_of(name))
	for i in 0..<len(name) {
		fmt.printf("%02x ", name[i])
	}
	fmt.println()
	for r in name {
		fmt.print(r, "")
	}
	fmt.println()
}
```

Output:

```
10 99 40
[20, 30, 40] 3 16
[10, 21, 30, 40, 50]
[21, 31, 40] [31, 40, 50]
4 16
5a 6f c3 ab
Z o ë
```

- Line 1: `b` was a full copy. `a[0]` is untouched. Five `int`s are 40 bytes.
- Line 2: the slice sees three elements and is itself 16 bytes.
- Line 3: writing through `s` changed `a`.
- Line 4: `s` and `t` overlap. Both see the element that became 31, `s` as its index 1 and `t` as its index 0.
- Lines 5–7: four bytes, three characters.

In the debugger, break after `s := a[1:4]` and expand `s` in Locals. You'll see its two fields. Compare its data pointer with `&a[1]` in the Watch panel.

### Task 4 — Stretch: a 2D grid in a 1D array

The surface map and the navigation grid will both be 2D grids stored in one flat array, since memory is one-dimensional.

1. Store a 6 × 4 grid of `u8` in a `[24]u8`.
2. Write `cell(grid: []u8, width, x, y: int) -> ^u8` returning a pointer to one cell.
3. Fill the grid so each cell holds `x + y * 10`. Print it as 4 rows of 6.
4. Write `row(grid: []u8, width, y: int) -> []u8` that returns one whole row as a slice, with no copying. Can you write `column` the same way? Why not? What does that say about which direction is cheap to walk?

## Check yourself

1. Where is `a[3]` in memory, given the address of `a` and the element size?
2. What are the two fields of a slice? How big is a slice of a million elements?
3. `b := a` for a fixed array, and `s := a[:]`. Which one copies the elements?
4. Why do procedures take `[]T` and not `[N]T`?
5. `s := a[1:4]`. Which elements of `a` does `s` see, and what is `len(s)`?
6. What does bounds checking protect you from? What does it cost?
7. Why is `len("Zoë")` 4?
8. What's the difference between `name[i]` and the `r` in `for r in name`?
9. A slice "doesn't own" its elements. What does that mean, and what could go wrong?
10. How is an Odin slice like a NumPy view?

> [!success]- Answers
> 1. At (address of `a`) + 3 × (size of one element).
> 2. A pointer to the first element and a length. 16 bytes, whatever the element count.
> 3. `b := a` copies every element. `s := a[:]` copies nothing. It makes a 16-byte view.
> 4. The length is part of a fixed array's type, so `[N]T` only accepts one length and copies the whole array. A slice accepts any length and copies 16 bytes.
> 5. `a[1]`, `a[2]`, `a[3]`. Length 3. The end index is excluded.
> 6. Reading or writing memory beyond the array, which would silently corrupt unrelated data. It costs one comparison per indexed access.
> 7. `len` counts bytes. In UTF-8, `ë` is two bytes.
> 8. `name[i]` is the byte at position `i`, a `u8`. `r` is a whole decoded character, a `rune`.
> 9. The slice only refers to memory that something else is responsible for. If that memory goes away or is reused, the slice still points there, and nothing reports it.
> 10. Both are a pointer into existing data plus a size. Both share memory with what they were sliced from, so writes show through.
